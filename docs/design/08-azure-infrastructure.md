# 08: Azure Infrastructure & Delivery

## 8.1 Resource inventory (production, lean profile)

> **No IaaS.** Every resource below is PaaS or SaaS. The inventory has no Virtual Machines, VM Scale Sets, AKS clusters or always-on Batch pools, and none may be added ([ADR-0005](adr/0005-sustainability-constraints.md)). Offline backfill and re-index work runs as **Container Apps Jobs inside the VNet** (§8.4), which exist only while a job runs. ACI Spot containers (preview) remain a documented alternative, with an Azure Batch Spot pool that scales to zero as its fallback ([ADR-0006](adr/0006-lean-hosting-profile.md)).

### 8.1.1 Resource logs and maintenance windows

**Every resource with resource logs sends them to `log-usnm`** through a diagnostic setting, all declared in one module, [`infra/modules/diagnostics.bicep`](../../infra/modules/diagnostics.bicep), except what the on-prem OCR nodes control, which goes to their own workspace, `usnm-ocr-log-<env>` (§8.3.1), so a node can't fill `log-usnm`'s cap. An audit policy (§8.5) flags any resource of those types that lacks one. The archival account is exempt (`usnm-archive-no-diagnostics`, a waiver on its own group's assignment): every workspace belongs to an environment and goes with its teardown, and the account outlives them all. When a workspace that outlives the environments exists, the account sends its blob writes and deletes there and the exemption goes.

| Resource                                                                        | Categories                                                                                                                                                                                               |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Log Analytics, Container Registry, VNet; storage queue, table and file services | All (`allLogs`). The nodes' workspace sends its own to itself, and the exchange account's queue service to the nodes' workspace                                                                          |
| Container Apps environment                                                      | `ContainerAppConsoleLogs`, `ContainerAppSystemLogs`. The environment's `appLogsConfiguration` is `azure-monitor`, so app and job logs arrive through this setting rather than the workspace's shared key |
| Cosmos DB                                                                       | `ControlPlaneRequests`, `PartitionKeyStatistics`                                                                                                                                                         |
| Blob service (data and tiles accounts)                                          | `StorageWrite`, `StorageDelete`, into `StorageBlobLogs` on the Auxiliary plan (below)                                                                                                                    |
| The OCR nodes' data collection rule (with `USNM_OCR_NODES`)                     | `LogErrors`, its only category: errors in collecting or transforming what the nodes' Azure Monitor Agent sends, into `DCRLogErrors` in the nodes' workspace; rows only when something fails              |

- **Per-request categories are left out** because they would use up the daily cap: blob reads (public tile fetches, and Quickwit's split reads on every search), Cosmos `DataPlaneRequests` and the per-query statistics (every ingest write), and Container Apps HTTP logs (every API request with its query string, which holds the search text; the API reports its requests itself, without paths or query strings, §8.1.2). Writes, deletes and control-plane changes are the audit trail.
- **Also left out:**
  - Application Insights is workspace-based, so its telemetry is already in `log-usnm`. Its resource logs would store every row twice.
  - Metrics-only resources (DNS zones, private endpoints, Container Apps and jobs) have no logs. Azure Monitor keeps their platform metrics for 93 days at no cost.
- **Retention** is the workspace's 30 days. Tables can go as low as 4 days, but 31 days are included in the ingestion price, so a 14-day limit would save nothing. The Application Insights tables (`AppRequests`, `AppMetrics`, `AppTraces`, `AppPageViews` and the rest) keep 90 days, included for Application Insights data. The control-plane audit tables, `CDBControlPlaneRequests` (Cosmos account and database changes) and `ContainerRegistryRepositoryEvents` (image pushes, pulls and deletes), are kept 365 days: 30 queryable, then long-term retention, read with a search job. They hold about 5 MB a month between them, so the year costs well under a cent a month ($0.02 per GB-month).
- **Daily cap and volume.** Prod's cap is 1 GB a day, dev's 150 MB (`dailyCapGb` in `infra/main.bicep`). From 30 September to 9 October 2026 (7 October left out) prod ingested 53 MB on an average day (27 to 83 MB): blob writes and deletes 18 MB, `AppMetrics` 17 MB, console logs 11 MB, `AppRequests` 5 MB, `AppTraces` 2 MB, everything else under 1 MB. About 1.6 GB a month, inside the free 5 GB. Since then (#231) the API no longer exports `api.requests` and `api.request_duration_seconds` (about 10 MB a day, copies of `AppRequests`) or writes a console line per request (about 1.7 MB), and the ingest job no longer forwards Quickwit's own line for each pushback it already logs (about 1.5 MB on average, 4 MB on a release day): about 13 MB a day less, and the blob logs are outside the cap, so about 22 MB a day counts toward it. When the cap is reached, ingestion of everything on the Analytics and Basic plans stops until the workspace's daily reset: logs, telemetry and every log-based alert (#231).
- **Blob writes on the Auxiliary plan.** `StorageBlobLogs` is the one table whose volume follows the bulk jobs: it has one row of about 1.2 KB per write or delete request (a `PutBlob`, or a `PutBlock` for each block and a `PutBlockList`), and every split a release writes, every Parquet part of the American Stories writer and every OCR output takes one or more. On 7 October 2026 those rows filled the then 0.15 GB cap at 17:46 ET and stopped all logging. The table is on the Auxiliary plan (`infra/modules/monitoring.bicep`), which the daily cap doesn't apply to. Auxiliary rows cost $0.15/GB ($0.05 ingestion and $0.10 processing, East US 2, October 2026) and aren't covered by the free 5 GB, which is for Analytics only: about $0.08 a month at 18 MB a day. Nothing queries the table (no alert, workbook or saved query). It stays queryable in Log Analytics with full KQL for its 30 days, more slowly than an Analytics table and at $0.005 per GB scanned; it can't feed a log search alert. A table's plan can change once a week.
- **Cap alert.** With alert emails set, _Log Analytics daily cap reached_ (severity 1, `infra/modules/monitoring.bicep`) fires on the workspace's own `OverQuota` event in `_LogOperation`. That table is free and keeps being written when the cap stops everything else (on 7 October 2026 the event arrived the minute logging stopped). Checked every 15 minutes over the last 30, one email per event and no "resolved" message, since the event marks when the cap was reached and ingestion stays stopped until the reset. Until the reset, a job that logs nothing may still be working: check `az containerapp job execution list` before stopping it.
- **Bicep writes the settings, not a `deployIfNotExists` policy.** Every resource here is created by the template, and nothing is created at runtime. The template can choose categories per resource, while the built-in policy initiatives enable whole category groups (`allLogs`/`audit`), which include the per-request logs above. Remediation would also need a policy identity with role-assignment rights, and it lags creation by minutes. The policy is therefore audit-only: it catches drift without writing anything.

### 8.1.2 Logs, telemetry and alerts: ingest jobs and API

The ingest and backfill jobs are short-lived and leave nothing on disk, so everything needed to diagnose a run goes out while it runs.

- **Console logs (Log Analytics).** `usnm-ingest` writes JSON lines to stdout, which arrive in `ContainerAppConsoleLogs`. The Quickwit writer's own output is read by the pipeline: warnings, errors and its readiness lines are forwarded as `target: quickwit` lines (except Quickwit's `tower_http` error for each ingest request it answers 429 or 503, which only repeats the pipeline's `Quickwit pushed back; retrying` warning), and its last 50 lines go into the error if it fails to start. While a release builds an index it logs `release progress` every 30 s and after each batch: documents sent and expected, MB sent, documents per second, 429/503 retries, free disk of the work directory, and the memory of the pipeline and of the Quickwit writer. A curate worker logs each batch's stages in the batch's span: `claimed` (attempt, lease owner and expiry), `waiting for a download slot` (seconds until the pacer's slot), `download slot granted` (seconds waited), `download started` (archive size, when the server sends it), `archive read` (pages, parts, MB, seconds), `issue items written`, and one outcome line: `curated` (pages, parts, archive size, and seconds from the download slot to the commit), `curation failed`, `curation timed out` or `throttled`. While it holds a batch, a separate task logs `curate progress` every 60 s: the stage (`waiting_for_slot`, `connecting`, `downloading`, `issues`, `committing`), seconds since the claim and in the stage, and the MB, pages and parts so far. It reads counters the worker updates, so it keeps reporting the stage of a batch whose work is stuck. A batch still unfinished 45 minutes after its download slot is abandoned: the worker logs `curation timed out` with the stage and counts, re-queues the batch as after any failure (the attempt counts), stops the download, and claims the next batch. 45 minutes is 3.6 times the p99 of a whole batch in the September 2026 backfill (745 s over 1,213 batches, wait for a slot included; the 3.8 GB archive took 974 s). The worker renews its 2 h lease when the slot is granted, so the limit ends well inside the lease however long the wait was, and an abandoned batch is released before another worker could claim it. A worker whose lease was taken during the wait (another worker claimed the batch after it expired) skips the batch without downloading it. Every failed command ends with one `command failed` line. Saved queries are in `ops/queries/`; `scripts/logs.sh --env <env> --query-name <query> [--span <timespan>]` runs one with the operator's Entra sign-in.
- **Traces and metrics (Application Insights).** The jobs get `APPLICATIONINSIGHTS_CONNECTION_STRING` and export OpenTelemetry spans (`release`, one `curate` per batch) and metrics (`ingest.docs_sent`, `ingest.bytes_sent`, `ingest.retries`, `curate.batches`, `curate.pages`, `curate.duration_seconds`, `release.docs_expected`, `work_disk_free_bytes`) directly, as `id-usnm-ingest` with an Entra token for `https://monitor.azure.com/` (Monitoring Metrics Publisher on the component). The connection string only names the ingestion endpoint; with local auth disabled it authenticates nothing. The exporters are flushed before the process exits.
- **Alerts** (`infra/modules/ingest-alerts.bicep`, log search alerts on the workspace, severity 2 unless noted, email through the action group; deployed with the jobs when alert emails are set). Each splits by a few columns that stay fixed while its condition lasts, and the email lists their values:
  - _Ingest or backfill job failed_: a `command failed` line, or a platform event of the ingest or backfill job for a replica that was killed or exited non-zero, in the last 15 minutes (checked every 5 minutes over 20, so the line a platform event repeats is still in view). Split by `Execution` and `Reason` (the error, cut to 180 characters, with URL query strings, `key=value` secrets and long opaque tokens masked). The expected stop of a full run that titles-sync didn't finish (`outcome: titles_left` on the line, or the error's "nothing was released: start the job again" for older images) is left out, as are the platform events that only repeat a replica's own line: its non-zero exit, and the job's backoff event right after it. Curate workers stop at their max runtime and exit 0 before the 24 h replica timeout, so a long backfill execution ends without this alert; a replica the timeout kills is still reported.
  - _Japanese OCR or audit job failed_ (severity 3): the same platform events for the Japanese OCR job `caj-usnm-jaocr-{env}` and its one-replica audit job `caj-usnm-jaone-{env}`, plus the first line of a Python traceback from either, in the last 15 minutes; not a replica the platform stopped because another failed. Split by `Execution` and `Reason`. These runs touch no published index, so they are kept out of the ingest alert, which reported failed measurement runs as ingest failures (7 October 2026).
  - _Ingest not progressing_ (severity 3): over the last 2 days, the ingest job's titles-sync stops since its last other ending either were not followed by another execution within 3 hours (`not started again`), or number 3 or more with the last leaving as many titles as the first (`no titles progress`). Every hour. Split by `Condition`, `Execution` (the last stop's) and `Detail` (stops, titles left at the first and last, when the last ended). `scripts/logs.sh --env <env> --query-name ingest-endings` lists the endings.
  - _Release stalled_: a release logged `building index` in the last two days (the ingest job's replica timeout, 48 h), hasn't finished, and has logged no `release progress` for 10 minutes (every 15 minutes). Split by `Execution` and `Detail` (the version, its start, the last progress line's time and pages sent).
  - _Backfill stalled_: backfill workers logged both at the start and at the end of the last hour but none curated a batch in it, and LoC isn't rate limiting (every 15 minutes). Workers that keep logging `curate progress` without finishing a batch trip this one. Not split: its only columns are counts.
  - _Backfill replica silent_: a backfill replica that has logged `claimed` has logged nothing for 15 minutes and hasn't ended: no `curation finished` or `command failed` line, and no platform event that stopped the replica or its execution (every 5 minutes, over the last day). A working replica logs at least once a minute, so a hung process, or one whose logs stopped arriving, is reported within about 20 minutes. Before the heartbeat, such a replica ran until the 24 h replica timeout. Replicas running an image from before the heartbeat are not checked. Split by `Replica` and `Detail` (its last line's time, message and batch).

The API (`usnm-api`) uses the same setup, shared in `crates/usnm-telemetry`, under the cloud role `usnm-api`:

- **Requests.** Every request except the `/healthz` and `/readyz` probes becomes one Application Insights request (`AppRequests`): name `<method> <route template>` (for example `GET /v1/aggregate`; `(site)` for the web app's files, `(no route)` for an unknown API path), result code, duration, and success, which is false only for a 5xx. `usnm.index_version` is the version the response came from (for search responses) or the one serving when it finished. `usnm.problem` is the problem `type` of an error response (`/errors/backend-timeout`), so the server-error alert can leave out slow searches (09 §9.1). It doesn't record the path, the query string or the client address (09 §9.4.2). There is no console line per request and no request count or duration metric: `AppRequests` has them, and until October 2026 those copies were about 12 MB of a 53 MB day (#231). Warnings and errors logged while a request is handled also go to `AppTraces`, linked to the request.
- **Metrics** (`AppMetrics`, every series every 30 s): `api.backend_duration_seconds` (search backend time for aggregate and hits, by `endpoint` and `outcome`), `api.cache_lookups` (by `layer`: `memory` or `blob`, and `result`: `hit` or `miss`), `api.rejected_queries` (by `reason`: `syntax`, `bad_parameter`, `unsupported`, `too_broad`, `rate_limited`, `bad_beacon`), `api.slow_searches` (searches that took longer than a visitor waits, once each when they end, by `endpoint` and `outcome`: `ok`, `timeout`, `error`, or `abandoned` when nobody asked about it any more; and searches refused because the queue for a computation slot was full or they waited in it too long, `outcome` `busy`, 06 §6.6), `api.search_queue_wait_seconds` (how long each visitor's search waited for a computation slot, 0 when one was free, by `endpoint` and `outcome`: `slot` or `busy`), `api.reference_reloads` (by `outcome`: `published` or `failed`), `api.prewarm_duration_seconds` (one cache warm-up run, by `trigger`: `startup`, `publish` or `searcher_restart`), `api.prewarm_queries` (by `outcome`: `ok`, `timeout`, `error` or `skipped` when the budget ran out), `api.prewarm_query_seconds` (each warm-up query that ran, by `endpoint` and `source`: `cache` when the answer came from the in-process or Blob cache, `computed` otherwise), `api.beacons` (valid page views from the site by `outcome`: `forwarded`, `bot`, `opted_out` for Do Not Track or Global Privacy Control, `other_origin`, `dropped` when the upload queue is full, or `off` without Application Insights) `api.index_version` (1, with the serving version in `index_version`), and the Quickwit searcher's caches (the sidecar's, or the searcher app's with `USNM_SEARCHER_APP`, #267) by `cache` (`split_footer`, `fast_field`, `partial_request`, `predicate`): `api.searcher_cache_bytes` and `api.searcher_cache_items` (what each holds, gauges) and `api.searcher_cache_hits`, `api.searcher_cache_misses` and `api.searcher_cache_evictions` (since the last report); and the searcher's thread pools and Tokio runtimes, to tell a cold search waiting on the search pool's cores from one waiting on downloads (#251): `api.searcher_pool_tasks` (the tasks a pool is running and has queued, by `pool`: `search` or `small_tasks`, and `state`: `ongoing` or `pending`, a gauge, for both pools at every read), `api.searcher_runtime_threads` (a runtime's worker threads, a gauge), `api.searcher_runtime_busy_ms` (how long its threads were busy since the last report, summed over them) and `api.searcher_runtime_capacity_ms` (the thread time they had in the same span, threads times the time since the last read; busy over capacity, summed over any span, is the busy share; neither is reported at the first read or after a searcher restart, when the busy time covers the searcher's whole life), by `runtime`: `main`, which does the downloads and opens the splits, and `blocking` and `non_blocking` if Quickwit starts them (a searcher doesn't). The searcher can't be reached from outside (the sidecar listens on localhost only, the searcher app has internal ingress only), so the API reads its Prometheus endpoint (`USNM_QUICKWIT_URL/metrics`) every minute (`USNM_SEARCHER_METRICS_SECS`). These reads are also how the API sees a searcher restart and warms it again (06 §6.5), so `0` turns that off too. It reports a cache gauge when it changes or every 15 minutes, the pool and runtime gauges at every read (a pool at 0 is a reading too), and a count only when it isn't zero, so a quiet replica sends a few cache rows an hour and about 7 thread rows a minute (§8.4). The first footer eviction of each searcher run logs `split footer cache evictions seen` once, without a cause (an eviction alone doesn't mean the footers don't fit, §8.4); a counter that goes down, in any cache or runtime, logs `the searcher restarted; its counters start again from 0`, and every count starts again from 0; a searcher that can't be read logs `searcher metrics unavailable; retrying quietly` once, and `searcher metrics available again` when it can. Warm-up queries are not counted in the request, backend or cache-lookup metrics; the searcher's caches, pools and runtimes count everything the searcher does, warm-up included.
- **Page views** (`AppPageViews`, cloud role `usnm-web`). The site posts one page view per page to `POST /v1/beacon` (06 §6.3.7, 07 §7.8), and the API forwards it as a `PageView` envelope through the same Entra-signed client, batched for up to 5 s or 100 page views and flushed at shutdown. Each has the page name (`search`, `status`, `privacy`, `not-found`), a URL with the page's path only, and `referrer_origin`, `utm_*`, `title`, `device_type` and `browser` in `Properties`. The visitor's address goes only in the `ai.location.ip` tag, from which ingestion derives `ClientCity`, `ClientStateOrProvince` and `ClientCountryOrRegion` before storing `ClientIP` as `0.0.0.0` (IP masking is on). The API's own requests keep no visitor address: their location columns are the Azure datacenter's (Boydton, Virginia). Nothing from a page view is logged.
- **Cache warm-up** (06 §6.5). Each run logs one `warm-up finished` line with `trigger`, `version`, `queries`, `ok`, `timed_out`, `failed`, `skipped`, `from_log`, `examples`, `examples_warm`, `cached`, `computed`, `gave_way_ms` and `ms` (06 §6.5 says how to read it). After a start, reading the cached searches logs `warm-up read the cached searches` (`cached`, `missed`, `ms`). A warm-up query that takes 1 s or more logs `slow warm-up query` (endpoint, example id, `source`, outcome, `ms`) and a failed one logs `warm-up query failed`; neither includes the query string. A start that reaches the readiness cap logs `warm-up still running at the readiness cap; reporting ready`.
- **Identity.** The app gets `APPLICATIONINSIGHTS_CONNECTION_STRING` and exports as `id-usnm-app` (selected by `AZURE_CLIENT_ID`), which has Monitoring Metrics Publisher on the component.
- **Queries:** `scripts/logs.sh --env <env> --query-name api-requests` (requests, 4xx, 5xx, 5xx rate and p50/p95 by route), `api-errors` (5xx by route and status, and the API's warning and error lines; a failed search names its cause: a Quickwit partial failure by category, such as `memory_limit×2`, with the failed split ids, a Quickwit status with its category, or the transport error, never Quickwit's own text, which can echo the query), `searcher-health` (the Quickwit sidecar's warning and error lines counted by module, without their text, and the app's restarts, OOM kills and probe failures from `ContainerAppSystemLogs`), `searcher-caches` (per replica and cache: MB and items held at the last report, hits, misses, evictions and hit rate in the span) and `traffic` (page views by day, page, referrer, `utm_source`, country, device type and browser; no rows, rather than an error, while `AppPageViews` is empty).
- **Search log** (06 §6.8, ADR-0012). `api.search_log` counts searches by `outcome`: `queued`, `dropped` (the queue was full), `written`, `lost` (beyond the retry limit, or not staged by 45 minutes after its day), and the exclusions `opted_out`, `bot` and `other_origin`. `api.search_log_writes` counts blob writes by `op` (`stage`, `close`) and `outcome` (`ok`, `error`). Search text is in neither, nor in any log line.
- **Search engine logs.** The Quickwit sidecar logs at `quickwit=info`, except `quickwit_serve::search_api` and `quickwit_search` at `warn` (`RUST_LOG` in `infra/modules/containerapp.bicep`). At info those two log every search request with its query, which is the visitor's search text (09 §9.4.2).
- **Alerts** (`infra/modules/api-alerts.bicep`, deployed with the API when alert emails are set). The log alerts read only rows of `usnm-api` from the API's own component (`_ResourceId`), since anyone with Monitoring Metrics Publisher on a component can write rows under any role name:
  - _API server errors_ (severity 2): at least 5 responses with a 5xx in 10 minutes that are also more than 2% of requests, or at least 10 search timeouts and busy refusals (checked every 5 minutes). Each condition met is its own alert, split by `Kind` (which one) and `TopRoute` (the route template and status with the most).
  - _Slow aggregate searches_ (severity 3): p95 of `/v1/aggregate` over 3 s in 15 minutes, with at least 20 requests and at least 3 of them over 3 s. A cold search takes 2–7 s and a cached one about 0.15 s, so one or two cold searches don't trigger it; a busy period right after a new index version (when every search is cold) can. Not split.
  - _Searches longer than a visitor waits_ (severity 3): at least 3 in an hour from `api.slow_searches`. Split by the `Endpoint` and `Outcome` with the most.
  - _Search capacity: searches waiting for a slot_ (severity 4, #238): on each of the last two days (24-hour spans back from the check) more than 10% of the searches that needed a computation slot waited over 3 s for one, that is the p90 of `api.search_queue_wait_seconds` above 3 s, with at least 20 such searches a day. `AppMetrics` has no buckets, so a 30 s export row's searches count as over when the row's mean wait is. Checked daily over 2 days, the most a log search alert can read, and stateless (Azure doesn't resolve rules checked less often than every 12 hours), so it emails every day the condition holds. Not split.
  - _Search capacity: replica CPU_ (`alert-usnm-api-replica-cpu-{env}`, severity 4, #238): a metric alert on the container app's `UsageNanoCores` when the replicas' 6-hour average is over 3 vCPU (of 4), checked hourly, where the app keeps a replica running (`minReplicas` above 0, prod). Not split by replica: Azure Monitor averages only the samples a series has, so a release's new replica, a series of its own, would be judged on its minutes of warm-up alone. The app's one series has a sample from every running replica every minute, so a warm-up is a few minutes of the 6 hours. The cost: while a second replica runs (the HTTP rule adds one past 50 concurrent requests, and the load is shared), the average can hide one replica over 3 vCPU beside a cooler one; the API workbook charts CPU per replica, which the week is judged on. Stateful. Both capacity alerts are planning signals for when to revisit a second searcher: the owner's condition is either holding for a week (#238, 10 October 2026), which the API workbook's capacity tiles show by day.
  - _Site or API unavailable_ (severity 1): a standard availability test `GET https://{domain}/` (the site and the API are one app; `/readyz` is already probed by Container Apps), every 15 minutes (`USNM_AVAILABILITY_FREQUENCY`: 300, 600 or 900 s) from East US, North Central US and West US, expecting 200 and a certificate valid for 7 more days, with retries. The alert fires when 2 of the 3 locations fail. Each test exists only once its hostname's certificate is bound. The results are written by the availability service, not sent by a client, so the component's `DisableLocalAuth` doesn't apply to them; Microsoft's list of features that don't work with Entra-only ingestion doesn't include availability tests. The first deployment should confirm rows in `AppAvailabilityResults`. Each run from one location costs $0.0005, so both tests at 5 minutes cost about $26 a month (09 §9.5).

**Workbooks** (`infra/modules/workbooks.bicep`, definitions in `infra/workbooks/`). Two Azure Monitor workbooks over the same workspace, listed under `appi-usnm-{env}` → Workbooks, and one over the OCR nodes' workspace, listed under `usnm-ocr-appi-{env}` (all three also in the resource group as Azure Workbook resources). - _usnm OCR nodes ({env})_ (deployed with `USNM_OCR_NODES`; default range 24 h; #296). Reads the nodes' workspace `usnm-ocr-log-{env}`, which holds the agent's tables and the nodes' component's. **No shared keys anywhere ([ADR-0009](adr/0009-entra-identity-only.md)).** Every caller is an Entra identity authorized by RBAC. **How the Quickwit sidecar authenticates (S-2).** From 0.9.0, when no access key is configured, Quickwit authenticates to Blob with the Azure SDK's default credential chain (`azure_identity` 0.21). This follows from the 0.9.1 source; it's confirmed against a real account on the first `quickwit` deployment (below). If it fails, the fallback is a localhost proxy in the `api` container that adds `id-usnm-app`'s bearer token to Quickwit's Blob requests. SAS of any kind, user-delegation included, is ruled out by ADR-0009. Our build of Quickwit ([ADR-0013](adr/0013-quickwit-from-our-fork.md)) uses the same credential, created once per process rather than for every search, so this holds for it too.

## 8.3 Networking

- **Public entry points:**
  - `usnewsmap.com`, `www.usnewsmap.com` and `api.usnewsmap.com` → Container Apps ingress, which forwards to the `api` container. It serves `/v1` and the built site ([ADR-0010](adr/0010-site-served-by-the-api.md)).
  - Quickwit binds to `127.0.0.1` inside the replica and has no ingress.
- **CORS:** the site calls the API on its own origin, so it needs none. The API still allows the domain, `www`, the app's own hostname and any `allowedOrigins`, GET only, no credentials. Researchers call the API directly; CORS doesn't restrict them.
- **Abuse protection without a WAF:** the per-client token bucket in the API (salted-hash keys, in memory), request timeouts, a query-complexity budget, and `maxReplicas: 2`. The replica cap turns abuse into slower responses instead of a larger bill.
- **Every app/job → data path uses both a managed identity and a private endpoint** ([ADR-0008](adr/0008-private-networking.md)):

  | Caller                                         | Target                                     | Identity                                                         | Network path                                                                                                                                          |
  | ---------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `api` container                                | Blob (`reference/`, `cache/`, `searches/`) | `id-usnm-app`                                                    | Private endpoint `pe-usnm-blob`                                                                                                                       |
  | `api` container (status page, read-only)       | Cosmos                                     | `id-usnm-app`                                                    | Private endpoint `pe-usnm-cosmos`, resolved through the same `privatelink.documents.azure.com` zone the ingest jobs use (same environment and subnet) |
  | `quickwit` sidecar (or the searcher app, #267) | Blob (`qw-index/`, read-only)              | `ca-usnm` system-assigned identity, or the searcher app's (§8.2) | Private endpoint `pe-usnm-blob`                                                                                                                       |

  | Backfill job (`caj-usnm-backfill`)             | Blob + Cosmos                              | `id-usnm-ingest`                                                 | Private endpoints `pe-usnm-blob`, `pe-usnm-cosmos`                                                                                                    |

| Browser | Tiles account (`stusnmtiles`) | Anonymous (public map data) | Public by design; no private data |

- **Authentication is identity-only everywhere:** `allowSharedKeyAccess=false` (no account keys, no service or account SAS) on `stusnmdata`, and `disableLocalAuth=true` (no Cosmos keys). Azure Policy **denies** turning either back on. Access is least-privilege RBAC on managed identities, and diagnostic settings record data-plane access. One exception: the ingest job's NFS scratch share (§8.4) is authorized by network, not identity ([ADR-0009](adr/0009-entra-identity-only.md#the-ingest-scratch-share-exception-proposed-in-pr-74)).
- **Steady state is private:** `publicNetworkAccess: Disabled` on `stusnmdata` and `cosmos-usnm`, and Azure Policy **denies** enabling it. The policy also covers Key Vaults. It exempts only the resource ids its assignment lists, which are the public tiles account and, with the OCR nodes on, the exchange account and the nodes' Key Vault (§8.3.1), so adding a tag exempts nothing. The only way in is through `pe-usnm-blob` and `pe-usnm-cosmos` from the VNet, resolved by the linked private DNS zones.
- **Guarded public-access window for Spot backfills (only if the ACI Spot alternative is used).** The default backfill runs as Container Apps Jobs inside the VNet and needs no window. ACI Spot groups can't join a VNet and have no stable egress IP, so for the duration of a Spot backfill or full re-index only (with a policy exemption for the deny above):
  1. The launcher records an `ops/public-access-window` item in Cosmos with the reason, an owner and an **expiry** (default 7 days).
  2. It sets `publicNetworkAccess: Enabled` on both accounts, with no IP rules (the Spot IPs are unknowable). Access still requires Entra tokens, and keys stay disabled by policy.
  3. When no unclaimed batches remain and the index run is complete, it sets `publicNetworkAccess: Disabled` again and closes the window item.
  4. A scheduled **`network-guard`** job runs hourly inside the VNet. It disables public access on any account that has it enabled without an open, unexpired window, so a crashed launcher can't leave the data services exposed.
  5. An Azure Monitor alert fires whenever `publicNetworkAccess` changes, and the change is recorded in the Activity Log.
- **Not private (accepted):**
  - the tiles account, which holds public map data only;
  - telemetry ingestion to Azure Monitor (an Azure Monitor Private Link Scope is part of the growth profile);
  - image pulls from the registry's public endpoint, which requires an Entra ID token (a private endpoint needs ACR Premium, ~$50/mo); images are code, not data;
  - LoC downloads.
- Anonymous public blob access is disabled on the data account (the tiles account is the only exception).
- **Hardening path (growth profile):** Front Door in front of both origins (edge cache, WAF); and an Azure Monitor Private Link Scope for telemetry. (The backfill already runs inside the VNet as Container Apps Jobs, §8.4, so the public-access window exists only if the Spot alternative is used.) With **Front Door Standard**, the API app must keep **external** ingress, because internal ingress is reachable only inside the environment. Lock it to Front Door by validating the `X-Azure-FDID` header in the API, plus IP allow-list rules generated from the published `AzureFrontDoor.Backend` service-tag CIDRs and re-synced by a scheduled job (Container Apps IP restrictions take CIDRs, not service-tag names). **Front Door Premium** can instead reach an internal environment over Private Link.

### 8.3.1 On-prem OCR nodes and the exchange account

Local machines re-read badly OCR'd pages ([ADR-0015](adr/0015-onprem-ocr-workers.md), #296). They're outside Azure and can't reach the private data lake, so they use a separate account. With `USNM_OCR_NODES` on (`infra/modules/ocr-exchange.bicep`):

- **Nodes:** Azure Arc-enabled servers on AlmaLinux 9 (or RHEL 10) in `rg-usnm-<env>`, outside the stack, each with a system-assigned managed identity whose tokens the agent serves at `localhost:40342`. The agent is locked down before it connects: one allowed extension, the Azure Monitor Linux Agent, no guest configuration, no incoming connections. The no-IaaS policy (§8.5) lists VMs, scale sets, AKS and Batch, not `Microsoft.HybridCompute/machines`; the machines are on-prem hardware. `scripts/ocr-node/onboard.sh` connects one ([operations](../operations.md#on-prem-ocr-nodes)).
- **Exchange account `stusnmo<suffix>`:** queues `ocr-priority`, `ocr-bulk` and `ocr-deadletter`, and container `ocr-out` (staging; a lifecycle rule deletes blobs after 30 days). Entra only, no shared keys. Public network access is on behind a firewall whose default action is Deny: it allows the node IPs (`USNM_OCR_NODE_IPS`, settings only) and `snet-cae`, through a Microsoft.Storage service endpoint on that subnet, with no trusted-service bypass. The public-network policy's assignment lists it by resource id. Its blob writes and deletes go to `log-usnm` like the other accounts' (§8.1.1); its queue logs, a row for every node request, go to the nodes' workspace (below).
- **Roles:** an Entra security group, `usnm-ocr-nodes-<env>` (object id in `USNM_OCR_NODE_GROUP`; `scripts/ocr-node/group.sh` creates it, since a deployment stack can't hold Graph resources), has Storage Queue Data Message Processor on `ocr-priority` and `ocr-bulk`, Storage Queue Data Message Sender on `ocr-deadletter` and a custom role on `ocr-out` that lists, reads and creates blobs but can't delete them, and nothing in the lake. Each node's Arc system-assigned identity is a member: `onboard.sh` adds it and `offboard.sh` removes it, with no provision. After a membership change, a node keeps its old access for up to about a day, until its cached token expires (ADR-0015). `id-usnm-ingest` has Storage Queue Data Contributor on the account (the seeder, dead letters) and Storage Blob Data Contributor on `ocr-out` (the copy-in job deletes what it has copied to `curated/ocr-local/`).
- **Monitoring, apart from the environment's** (`infra/modules/ocr-node-monitoring.bicep`): a Log Analytics workspace `usnm-ocr-log-<env>` with its own daily cap (0.1 GB to start) and a workspace-based Application Insights component `usnm-ocr-appi-<env>` on it, both with local auth off. The nodes' group has Monitoring Metrics Publisher on that component and nothing on `appi-usnm`: the role lets its holder write any telemetry under any role name, and Application Insights ingestion has no IP firewall, so on the environment's component a node, or a stolen node token, could write rows the API alerts read or fill `log-usnm`'s cap (ADR-0015 decision 8). Each node runs the Azure Monitor Agent, the only extension its Connected Machine agent allows. One data collection rule, `usnm-ocr-dcr-<env>`, sends syslog at Warning and above, the worker's own lines at Info and above (its unit logs to `local0`), CPU, memory, disk and network counters every 60 s and VM insights' log-based metrics (`InsightsMetrics`, for the Arc machines' Insights pane; no Map) to the nodes' workspace, on the Analytics plan, with the exchange account's queue logs and the rule's errors (`DCRLogErrors`, §8.1.1): about 20 to 45 MB a day per node before the worker's telemetry, estimated. The worker's traces and metrics go to the nodes' component with the node's identity (`OCR_NODE_APPINSIGHTS`). One node can still fill the nodes' cap (a crash loop, debug logging), which stops node monitoring until the reset and nothing else; `alert-usnm-ocr-node-volume-<env>` fires when a node sends more than a tenth of the cap in an hour, through the agent and its telemetry together, and `alert-usnm-ocr-log-cap-<env>` when the cap is reached. `onboard.sh` installs the agent and associates the machine with the rule, since the template doesn't declare the machines; `offboard.sh` removes both. Saved queries, run against the nodes' workspace: `ocr-node-health` and `ocr-node-errors` ([operations](../operations.md#on-prem-ocr-nodes)).
- **Key Vault `usnmocrkv<env><suffix>`** (`infra/modules/ocr-vault.bicep`, #296, #295): the operator's node-setup secrets, which aren't Azure credentials. They are `rhel-activation-key` and `rhel-org-id`, the Red Hat activation key and organization id that register a RHEL node, and `rhel-offline-token`, a Red Hat API offline token the Proxmox hosts use to fetch RHEL images through Red Hat's image API. The maintainer sets them with `az` ([operations](../operations.md#on-prem-ocr-nodes)); `onboard.sh` will read them (next PR) with the operator's sign-in and pass them to the node over ssh's stdin, so they're never written to disk on the operator's machine, the node or the Proxmox host, or committed. Azure RBAC only, no access policies: the operators in `USNM_OCR_KEYVAULT_ADMINS` (object ids, settings only) have Key Vault Secrets Officer, and the nodes have nothing. Public network access is on behind a firewall whose default action is Deny, allowing only the node IPs (`USNM_OCR_NODE_IPS`: the operator's home IP), with no trusted-service bypass; the public-network policy's assignment lists it by resource id like the exchange account. A private endpoint would cost about $7.30 a month and the operator's machine couldn't reach it without a VPN; ADR-0008 is about app and job paths to the data, and no app, job or node reads this vault. Soft delete and purge protection are on in prod (90 days); elsewhere soft delete keeps a deleted vault 7 days and `teardown.sh` purges it (ADR-0017, open question 1). Its audit log (`AuditEvent`, every read, write and refused request) goes to `log-usnm`. Turning `USNM_OCR_NODES` off deletes it with the rest; in prod it then stays soft-deleted for 90 days, holding its name, (7 days outside prod). Turning the nodes back on within that time works because `provision.sh` first recovers this environment's soft-deleted vault, matched by the resource group it was deleted from, with its secrets, and the stack takes it over again.

## 8.4 Compute sizing notes

- **`api` container:** 0.25 vCPU / 0.5 GiB. Rust handles cached responses at hundreds of requests per second on this, so the searcher is the bottleneck.
- **`quickwit` container:** 3.75 vCPU / 7.5 GiB, the rest of the Consumption profile's 4 vCPU / 8 GiB replica (since 9 October 2026, #251: on the American Stories index the searcher was CPU-bound at 2.0 of 2.0 vCPU). It started at 1.0 vCPU / 2.0 GiB, then 2.0 / 4.0. It reads splits from Blob on every search and caches only in memory, with the capacities in `infra/quickwit/searcher.yaml`: split footers (`split_footer_cache_capacity`, 256 MB), fast fields (1 GB), partial results (32 MB) and predicate results (32 MB); no `searcher.split_cache` is configured, so nothing is kept on disk. A disk split cache on the replica's ephemeral storage is a possible follow-up for cold searches.
  - **Image ([ADR-0013](adr/0013-quickwit-from-our-fork.md)).** Our build of Quickwit v0.9.1 (`quickwit/quickwit-usnm`, from the fork `tgoodyear/quickwit`), pinned by digest in `infra/quickwit-image.json`. Upstream's Azure client opens a new connection and does a full TLS handshake for every Blob request, and builds a new client and credential for every search; in dev that was 2.0 to 3.0 s of runtime work per cold search. Ours shares one pooled HTTP client and one token credential across the process: 0.09 to 0.26 s, and a cold median of 0.18 s against 0.72 s (#251). `QW_AZURE_POOL=false` on the sidecar restores upstream's client without a new image.
  - **Threads (#251).** Quickwit 0.9.1 searches each split on one thread of its search pool and runs splits in parallel. Left to itself it sizes that pool from Rust's CPU count, which rounds the 3.75 quota down to 3, and runs every blob download on one tokio thread (a third of its CPU count, rounded up). The sidecar sets `RAYON_NUM_THREADS=4` (the search pool), `QW_TOKIO_RUNTIME_NUM_THREADS=4` (at 2 the runtime was 96 to 99% busy through a cold-search test while the search pool sat idle) and `QW_NUM_CPUS=4` in `infra/modules/containerapp.bicep`. `max_num_concurrent_split_searches` (48) is the number of splits downloading at once, not CPU work, and `warmup_memory_budget` (3 GB, Quickwit's default is 100 GB) pauses new downloads once their estimated memory passes it. It is an admission budget, not a ceiling: splits are admitted on a 10 MB estimate and their actual use can run past it. The headroom is about 5.4 GB after the caches and aggregation limit; at 24 slots the whole searcher used 0.8 GB during cold searches. Spike S-2 measured p95 at 1.0 vCPU; the cold-search load test (06 §6.5) is re-run at 3.75 vCPU for #251.
  - **The split footer cache should hold every footer** of the serving version (#125). A search reads each split's footer (its hotcache: the term dictionaries' index and the file list) before anything else; a footer the cache dropped is fetched from Blob again, so every cold search pays for it once more. Each release logs `footer_bytes` (all the footers of an index) and `largest_footer_bytes` on its `index layout` lines and records them in the manifest (§8.1.2, 05 §5.5.1). The API reports what the cache does (`api.searcher_cache_*`, §8.1.2): the footers fit when the release's footer total is below `split_footer_cache_capacity` and, after the warm-up, footer misses and evictions stop coming. Evictions alone prove nothing: Quickwit 0.9.1 also counts replacing an entry as an eviction, and after a publish the cache drops the old version's footers. Size it from the release's footers, summed over every index of the version, plus headroom; Quickwit reads `256MB` as 256,000,000 bytes, and the memory comes out of the same 7.5 GiB as the fast field cache and the aggregation limit ([operations](../operations.md#searcher-caches)).
  - The sidecar is now at the largest size the Consumption profile allows. Further latency levers are on the index side (#251: fewer, larger splits, less American Stories text to search) or a second searcher (#239).
  - A second replica adds **concurrency, not per-query speed**: each API talks only to the Quickwit sidecar in its own replica over localhost, so one query's splits aren't spread across replicas. Per-query latency levers are sidecar size (already 3.75 vCPU / 7.5 GiB, the most alongside the 0.25/0.5 API within the 4/8 replica limit), the cache and the index layout.
  - It stays on Container Apps in every scenario; there is no VM or AKS fallback.
  - **Searcher app (#267, as built, off by default).** Every new API image, which also carries the site, starts a new revision of `ca-usnm` and with it a new sidecar with empty caches and a warm-up. With `USNM_SEARCHER_APP` the searcher runs as its own app, `usnm-search-ca-<env>`, and API and web deploys don't touch it: the sidecar's container (image, `searcher.yaml`, 3.75 vCPU / 7.5 GiB, threads, probes, plus a readiness probe), listening on all interfaces and advertising its replica's address, with internal ingress only (`http://usnm-search-ca-<env>`, port 80 to 7280) and one replica (in prod always; elsewhere it scales to zero with the API). One replica because a second would start cold and split the cache hits; more capacity is a cluster (#239). Its system-assigned identity has the sidecar's role, Blob Data Reader on `qw-index` alone; `ca-usnm` then has `api` alone (0.25 / 0.5), and its `USNM_QUICKWIT_URL` names the app. It keeps its system-assigned identity and role, unused, so the old revision's sidecar can read the index until the new revision is ready and a roll back's sidecar can read it at once; a follow-up change drops them once the searcher app is kept ([operations](../operations.md#searcher-app)). A second API replica then shares the one searcher instead of bringing a cold one. The API reads the searcher's metrics over that address as it did over localhost, and when they show a restart (a new Quickwit image moves with a provision and restarts the searcher alone) it runs its start's warm-up again (06 §6.5). Searches cross the environment's network instead of localhost. At list prices the split is about cost-neutral (09 §9.5). It is off until measured: the API to searcher latency, deploys leaving the searcher's caches, and the idle billing of each app ([operations](../operations.md#searcher-app)). The decision to keep it is pending those numbers.
- **Weekly updates:** LoC has no notification of new batches, so `caj-usnm-ingest` polls: on its `USNM_INGEST_CRON` schedule (prod will use `17 3 * * 1`, Mondays 03:17 UTC) it runs `usnm-ingest run`, which fetches LoC's batch listing once (one request, about 3,000 batches), queues new batches and new versions, curates them with one worker through the shared download pacer, fetches title records for titles not yet catalogued (one every 3.5 s, waiting out LoC's one-hour blocks until 8 h after the start, 04 §4.6), and releases a delta. When LoC has published nothing, the run queues nothing, curates nothing, fetches no title records once the catalog has every listed title, logs `no newly curated batches; nothing to release`, and exits 0. Curation in a run stops claiming batches 6 h after the start (`--curate-max-runtime-secs`) and titles-sync sends nothing after 8 h (`--titles-max-runtime-secs`), so a large publication can't push the release past the replica timeout (48 h for the ingest job, #172): what was curated is released and the rest stays queued. A full release (asked for, or forced) goes ahead only once titles-sync has fetched every title LoC has, with no failed fetches; otherwise the run fails without releasing and the next execution continues the sync. One worker curates about 15 batches an hour (an average archive is 0.8 GB, at the 3.9 MB/s per worker measured in S-1, 04 §4.1.1), so a run takes up to about 90 new batches. For more, start the backfill job as well: its workers share the queue and the pacer with the run. A batch that keeps failing is re-queued by each run's enqueue and costs one download a week until it is fixed or removed from the listing.
- **Writer scratch disk.** The Quickwit writer in `caj-usnm-ingest` keeps its write-ahead log, the splits it builds and its merges on an NFS Azure Files share, `qw-scratch` in `stusnms…` (provisioned v2 SSD, 128 GiB by default, `USNM_INGEST_SCRATCH_GIB`), mounted at `/scratch` and reached through its own private endpoint, `pe-usnm-file`. A replica's own disk is 8 GiB by the documentation for anything over 1 vCPU (about 19.5 GiB in practice, about 13 GiB free at the start of a release), and the September 2026 deltas filled it: indexers died with "No space left on device" and merges failed. Sizing, at about 23 KB of index per page (measured on the prod releases and on a local build of OCR-like text): the largest merge reads splits holding under 200,000 pages and writes one (`split_num_docs_target: 100000`, 05 §5.5.1), under 10 GB together, one merge at a time (`merge_concurrency: 1`); plus the write-ahead log (4 GiB cap), the uploaded-split cache (4 GiB) and the split being built (about 2 GiB). That is about 20 GB. The share was sized at 128 GiB for million-page splits, which the writer's memory rules out (next item); a smaller share is a possible saving, but its size also sets its throughput. The release refuses to start with less than three quarters of the share free, which also catches a share that isn't mounted, and removes a previous run's writer data first: on a persistent share, an old write-ahead log would otherwise replay into an index a published version may list. NFS needs no keys, but it has no identity either: access is by network, through the private endpoint only, and anything in the Container Apps subnet can reach it. That is an exception to Entra-only access, with its limits recorded in [ADR-0009](adr/0009-entra-identity-only.md#the-ingest-scratch-share-exception-proposed-in-pr-74). Shared key access stays disabled on the account. Container Apps can't mount NFS shares that require encryption in transit, so that setting is off for NFS; the traffic stays in the VNet. An init container (the pinned Quickwit image, which runs as root) hands `/scratch/usnm` to the pipeline's user, and the ingest container drops to 3.75 vCPU / 7.5 GiB so the replica stays within 4 vCPU / 8 GiB (the September releases peaked at 6.2 GiB for the pipeline and writer together; the writer's memory is the next item). Cost: about $13 a month for 128 GiB, $7.30 for the private endpoint and $0.50 for its DNS zone (09 §9.5). Setting `USNM_INGEST_SCRATCH_GIB=0` removes the share; the writer then works on the replica's disk, too small to merge large indexes.
- **Writer memory.** The pipeline and the Quickwit writer share the ingest container's 7.5 GiB (the Consumption profile's 8 GiB per replica, less the init container). The pipeline itself stays under 400 MB, plus, with American Stories' text (04 §4.9), the text of the batch it is indexing (logged per batch as `text_mb`; at about 25 KB a page, the writer's estimate, about 200 MB for an average batch of about 8,000 pages and proportionally more for large ones). The writer's use has three parts: indexing (the 1 GiB indexing heap and up to 1 GiB of in-memory ingest queue), merging, and uploading splits. The upload is the large one. Quickwit 0.9.1 sends a split to Blob as 100 MB blocks, up to 100 at once, and reads each block into memory before sending it, so a split of S GB holds about min(S, 10) GB until it is uploaded. Merges don't overlap the upload: with `merge_concurrency: 1` the next merge starts only once the last merged split is published. Measured in the October 2026 full release (7.8M pages, `quickwit_rss_mb` in `release progress`): 5.0 GB at most while indexing and uploading 110,000-page splits (about 2.6 GB each), 3.2 GB at most while only merging them, and 7.0 GB 30 s after a million-page merge (about 23 GB) began to upload, before the writer was killed. Hence `split_num_docs_target: 100000` at first: a merged split held about 110,000 pages and never 200,000 (about 4.6 GB). The common-word pairs (05 §5.5.3) make a page about 37 KB of index rather than 23 (1.6×, measured on 90,745 real pages), so the target became 60,000: about 66,000 pages (2.4 GB) and never 120,000 (4.4 GB), so the bounds below still hold. American Stories' text and its pairs (05 §5.5.4) make a page it covers about 74 KB, so the target is now 30,000, for the same bounds. The measured peak is 5.2 GB with the pipeline, of the 8.05 GB (7.5 GiB) limit. The worst case is a 4.6 GB split uploading while the writer indexes at its October peak less that release's 2.6 GB upload (about 2.4 GB), plus the pipeline: about 7.4 GB. That needs a merge of already-merged splits during ingest, and Quickwit runs the merges that remove the most splits per byte first, so those wait behind the first-round merges: none ran during the October ingest. After ingest, when they do run, the worst case is about 5.3 GB. Options weighed:
  - _More memory:_ the Consumption profile can't give a replica more than 8 GiB. A Dedicated workload profile can, but any Dedicated profile in the environment adds the Dedicated plan management fee, $0.10 an hour or about $73 a month, close to the whole $80 target (09 §9.5). That rules out a permanent one, but not one that exists only while a full rebuild runs: after the 2026-10-05 full rebuild with common-word pairs was killed for memory at 7.5 GiB, 6.5 h in, with sampled peaks of 6.0 GB (#172), full rebuilds run on an E4 profile (4 vCPU / 32 GiB, about $0.39 an hour while the job runs) that is added for the rebuild and removed afterwards (`USNM_DEDICATED_PROFILE`, `USNM_INGEST_ON_DEDICATED`; docs/operations.md, "Full rebuild"). Weekly deltas stay on Consumption.
  - _Fewer blocks in flight:_ the 100-block limit is fixed in Quickwit 0.9.1's Azure storage (not a setting); changing it means another commit on our Quickwit fork and a new build ([ADR-0013](adr/0013-quickwit-from-our-fork.md)).
  - _Smaller splits (chosen):_ a setting, measured at this size in prod, at the cost of cold searches opening about 220 splits of the full corpus instead of about 24, about 360 at 60,000 pages with the common-word pairs, and about 800 at 30,000 pages with American Stories' text (05 §5.5.1).

  If the writer dies anyway, the release says so: the pipeline owns the writer's process, records how it ended, and fails with, for example, "the Quickwit writer was killed by signal 9 (SIGKILL): it ran out of memory (the container's cgroup counts 1 out-of-memory kill; the container's memory limit is 7.5 GiB)" and the writer's last lines, instead of the "connection refused" of its next request. It doesn't restart the writer: the merge planner would plan the same merge again with the same memory, and nothing has been published, so the job can simply be started again once the cause is fixed.

- **Merge wait.** The release waits for merges up to `USNM_MERGE_TIMEOUT_SECS` (4 h by default; a deployed setting). In the October 2026 release, a merge of 10 splits into one of about 110,000 pages took about 77 s while nothing else ran (241 splits down to 70 in 24 minutes), and merges fell behind ingest by about 8 an hour. So the merges left after ingest take about 30 minutes for 7.8M pages and about 1.7 hours for 23.8M pages (about 73 merges), plus up to 5 final merges. Million-page splits would have needed 23 merges of about 15 to 20 minutes each on top for the corpus, about 8 hours of merging in all, too long to fit a full rebuild into the 24 h replica timeout. A full rebuild of 23.8M pages sends for about 8.8 h (at the 750 pages a second of October 2026; 10.7 h at 620), so with the catalog synced first the execution takes about 11 h, and at most 22 h 45 min by the bounds in `infra/modules/ingestjobs.bicep`. With common-word pairs (#154) the first full rebuild sent only 230 to 460 pages a second (2026-10-05), so sending takes up to about 29 h and the run about 41 h; that run started with a 24 h timeout it couldn't finish within, so the ingest job's replica timeout is now 48 h (#172). A release can't resume in a new execution: a timeout loses the whole rebuild, so the timeout must cover the slowest full run. The backfill and Japanese OCR jobs keep 24 h.
- **Backfill on Container Apps Jobs (implemented).** Spike S-1 measured the whole corpus at ~175 worker-hours of curation (bzip2-bound, 04 §4.1.1). That is small enough to run inside the VNet on the Consumption profile: `caj-usnm-backfill` starts **N = 4** replicas of `usnm-ingest curate` (1 vCPU / 2 GiB each), which claim batches from Cosmos until none remain. LoC's bulk limit (10 requests per 10 minutes per IP), not CPU, sets the pace: downloads are spaced 75 s apart across all workers (04 §4.4), so the corpus takes about 2.5 days. Each worker stops claiming batches 22 h after it starts (`--max-runtime-secs 79200`): a batch still waiting for its download slot goes back to the queue without losing an attempt, a batch already downloading is finished (the 45-minute watchdog bounds it), and the worker logs `max runtime reached; claiming no more batches` with the number still queued, then `curation finished`, and exits 0. So an execution whose replicas all run from its start ends by about 22 h 45 min, inside its 24 h replica timeout, and doesn't raise the job-failure alert. A replica the platform retries after a crash (`replicaRetryLimit: 1`) counts its 22 h from its own start, so it can still reach the timeout; the crash has already raised the alert by then. The operator starts the job again until the queue is empty, or schedules it while a backfill lasts with `USNM_BACKFILL_CRON` (a UTC cron, e.g. `0 9 2-4 10 *`; empty is manual), which deployments keep. The backfill is a one-off for the initial corpus, or for a publication too large for the weekly run; batches LoC publishes later reach the site through the weekly ingest run. At list prices that is ~$20–30 of vCPU and memory time, before the monthly free grant; workers are billed while they wait for a slot. It needs no launcher, no public-access window and no `network-guard`. Workers stream each archive and parse it as it downloads, verifying the sha256 before committing, so they need no scratch disk. A replica that dies leaves its batch leased; another replica or the next run claims it when the lease expires. `caj-usnm-ingest` then runs `usnm-ingest run`, which finds nothing left to curate and builds the first base index.
- **Alternative: backfill on ACI Spot** (not built):
  - The `backfill` launcher (a tiny Container Apps Job inside the VNet) marks every batch `queued` in Cosmos, opens the public-access window (§8.3), and creates **N = 8** Spot container groups (2 vCPU / 4 GB each; N is bounded by LoC download politeness, not CPU).
  - Each group repeatedly claims the next `queued` batch from Cosmos with a conditional lease patch until none remain, then exits (`restartPolicy: OnFailure`). The launcher then deletes the groups and closes the public-access window.
  - **Evictions are harmless.** Microsoft's ACI Spot documentation states that evicted container groups "are automatically restarted without requiring any action from the customer." As insurance against preview behavior changes, the launcher also runs a **reconcile loop** every 5 minutes while a backfill is active: any group that is missing, stopped or failed is redeployed, including the singleton full-index group, until no unclaimed batches remain and the index run is complete. A batch claimed by an evicted worker becomes claimable again when its lease expires (default 30 minutes). Batch processing is idempotent (new attempt path plus a Cosmos commit), so a retry never corrupts committed data.
  - The per-group disk limit of **50 GB** is enough, because each batch archive is streamed and processed, then discarded.
- **Full index build:** one ACI Spot group (4 vCPU / 16 GB) runs the Quickwit indexer against the curated Parquet, **one curated partition at a time**, recording completed partitions in the Cosmos `index_runs` item.
  - After an eviction it resumes at the first unfinished partition.
  - Partial partitions are discarded because splits are published only when a partition completes. The exact mechanism (per-partition commit or file-source checkpoints) is validated in S-2.
- **Fallback:** if ACI Spot is unavailable or evictions stall progress, the same image runs on regular-priority ACI (about 3× the cost, still ~$100) or on an **Azure Batch Spot pool** that scales to zero (container tasks, one per batch). Using the Batch fallback needs a time-boxed exemption from the "Not allowed resource types" policy for the `rg-usnm-prod-spot` resource group.

### 8.4.1 Quickwit metastore: one writer, many readers

Quickwit's **file-backed metastore** (a JSON file per index on Blob) doesn't support concurrent writers. Scaling a node that _writes_ it would risk corrupting metadata. The design therefore separates readers from the writer:

| Process                                                                  | Quickwit roles                                                                                      | Metastore access                                                                                                                                           | Count                                                                                                            |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `quickwit` sidecar in each `ca-usnm` replica, or the searcher app (#267) | `searcher` (plus the metastore service pointed at the file-backed URI with `#polling_interval=30s`) | **Read-only.** It picks up newly published splits by polling. No indexer or janitor roles run here, and the identity has only Blob _Reader_ on `qw-index/` | 1–2                                                                                                              |
| `index` job (weekly incremental: Container Apps Job)                     | `indexer` + `janitor`, embedded in the job container                                                | **Sole writer.** It only ever writes a **new delta index** (`pages-delta-{date}-{n}`), never an index that a published version already lists               | ≤ 1, enforced by a Cosmos `ops/quickwit-writer` lease (ETag compare-and-swap, 2-hour TTL, renewed while running) |
| Compaction / full rebuild (`caj-usnm-ingest` with `--full`)              | `indexer` + `janitor`                                                                               | Sole writer of a **new base index** (`pages-base-{date}`)                                                                                                  | 1                                                                                                                |

**Index versions are immutable sets of sealed indexes.** An `index_version` names an explicit list of Quickwit indexes in `current.json`: one base plus zero or more deltas, e.g. `["pages-base-20261001", "pages-delta-20261008-1", "pages-delta-20261015-1"]`.

- **Sealing:** once an index appears in a published version, it's sealed. No job writes to it again; replacement or deletion only happens by building a new base.
- **Explicit index lists:** the API passes exactly the listed index ids to Quickwit (multi-index search with the same doc mapping). No query touches a new delta until a new `current.json` lists it. A given `v` therefore always returns identical results, and rolling back to the previous `current.json` restores the exact previous set.
- **Warming new indexes (S-2):** a read-only searcher reads the metastore's index list only at startup. Polling then picks up new splits of the indexes it knows, but a search naming an index created later fails with "could not find indexes". Looking the index up by id (`GET /api/v1/indexes/{id}`) loads it from Blob and adds it to the polled set. The API therefore looks up every index a new `current.json` lists before it swaps in that version (`SearchBackend::prepare`). If any lookup fails, it keeps serving the previous version and retries on the next poll. No sidecar restart is needed.
- **Weekly increments** add new pages as a new delta, then publish a new version listing base + all deltas.
- **Replacements** (new batch versions, OCR reprocessing) and **title-metadata changes** can't be applied to sealed indexes. They're recorded as pending in Cosmos and applied by the next **compaction**: a full rebuild into a new base by the ingest job (a few dollars), which also clears the deltas. Compaction runs monthly, or sooner once there are 8 deltas or when pending replacements are flagged urgent. Until then the previous text and place assignments keep serving, consistently with their reference snapshot.
- **Garbage collection:** `usnm-ingest prune` (#245), run by hand as an ingest job execution, deletes through Quickwit every index that neither the serving version nor its rollback (`previous_version`) names, nor a published version newer than the serving one: older versions and unpublished rebuilds. It takes the writer lock, lists what it would delete unless given `--delete`, and refuses without a readable `current.json` ([operations](../operations.md#prune-old-index-versions)).
- **Azure AI Search (growth profile)** can't query several indexes in one request. That backend publishes only on compaction (a new index per version), and weekly increments wait for it.

S-2 checked this on Quickwit 0.9.1 with a file-backed metastore: a searcher-only node (`enabled_services: [searcher, metastore]`, `#polling_interval`) serves the writer's indexes, never writes the metastore, and serves indexes created after it started once they are warmed as above. CI repeats this on every change (the `quickwit` job). **Fallback:** a PostgreSQL metastore (Azure Database for PostgreSQL Flexible Server, Burstable B1ms, ~$13–15/month). It supports any number of Quickwit nodes, but puts a typical month at ~$86, over $80.

## 8.5 Infrastructure as code

- **Bicep** modules under `infra/`, deployed as **one deployment stack per environment** (`usnm-<env>`, subscription scope; [ADR-0011](adr/0011-deployment-stacks.md)). A resource removed from the template is deleted on the next deployment (`actionOnUnmanage: deleteResources`), and a deny assignment blocks deletes of any managed resource outside the stack (`denyDelete`). Settings live in `.azure/<env>/.env` and reach the template through `infra/main.bicepparam`. `scripts/bootstrap.sh` stands an environment up, `scripts/provision.sh` redeploys it, and `scripts/teardown.sh` removes it. The first slice is implemented in [`infra/`](../../infra/README.md). It covers the network, private endpoints, the data, tiles and Cosmos accounts, identities and RBAC, the Container Apps environment and the API app (which serves the site), monitoring, the budget and the guardrail policies. The Quickwit sidecar is in place behind `searchBackend` (`USNM_SEARCH_BACKEND=quickwit`) and waits on the first published index. The ingest and backfill jobs are in place behind `ingestJobs` (`USNM_INGEST_JOBS=true`). DNS follows.
- Modules: `network` (VNet, subnets, private endpoints, private DNS zones), `containerapps-env`, `containerapp`, `job`, `aci-spot` (backfill groups, deployed by the launcher), `storage`, `cosmos`, `dns`, `monitoring`, `budget`, `rbac`. Growth-profile modules behind parameters: `frontdoor`, `acr`, `keyvault`, `aisearch`.
- **Parameters per environment**: `dev` (scale to zero, LRS, small sample corpus of ~1M pages), `prod`.
- Lint with `bicep lint` plus PSRule for Azure in CI. No `what-if` preview: deployment stacks don't support it yet ([ADR-0011](adr/0011-deployment-stacks.md)).
- Policy: deny public blob access, require HTTPS/TLS 1.2+, require diagnostic settings (**as built:** `usnm-audit-diagnostic-settings`, `auditIfNotExists` on every resource type with resource logs, §8.1.1), allowed locations, and a built-in **"Not allowed resource types"** assignment that blocks `Microsoft.Compute/virtualMachines`, `virtualMachineScaleSets`, `Microsoft.ContainerService/managedClusters` and `Microsoft.Batch/batchAccounts` on the project resource groups, so VMs can't creep in. Also: **deny** `allowSharedKeyAccess != false` on storage, **deny** `disableLocalAuth != true` on Cosmos, and **deny** `publicNetworkAccess != Disabled` on storage and Cosmos accounts except the ids in the assignment's `publicAccountIds` (the tiles account). A Spot window would need a policy exemption, and closing the account afterwards is a separate step.

## 8.6 CI/CD (GitHub Actions)

```mermaid
flowchart LR
  PR[Pull request] --> CI1[Rust: fmt · clippy · test · deny · audit · fuzz smoke]
  PR --> CI2[Web: typecheck · lint · vitest · playwright · axe]
  PR --> CI3[Infra: bicep lint · PSRule]
  PR --> CI4[Security: CodeQL · secret scanning push protection · Dependabot]
  PR --> PREV[preview revision of the app against dev]
  M[merge to main] --> B[build & sign images · SBOM · push ACR (OIDC)]
  B --> DEV[roll dev onto the images]
  DEV --> SMK[smoke + k6 short load]
  SMK --> GATE{{manual approval: prod environment}}
  GATE --> PROD[roll prod · new revision 10% → 100%]
  PROD --> POST[prewarm cache · synthetic checks]
```

- **As built:** `ci` runs every check on each PR and push. On `main`, after all of them pass, `publish` runs once per environment listed in `USNM_DEPLOY_ENVIRONMENTS`: it pushes the images to that environment's registry and rolls its API app, which carries the site, onto the commit, applying the searcher's config (`infra/quickwit/searcher.yaml`) first if the running one differs: to the sidecar, or with the searcher app (#267) to that app, waiting for its new revision before the API rolls. An API image never restarts the searcher app. Other stack changes need `scripts/provision.sh`, which CI's identity can't run; a merge that makes one gets a warning from the `stack change needs a provision` job. (The October 2026 Quickwit timeout fix sat undeployed for this reason: it was in the Bicep, and only the API image rolled.) Each environment is a GitHub Environment restricted to `main`, with its own variables and OIDC trust (§8.9). Only the commit `main` currently points at deploys, so a slow run for an older commit can't overwrite a newer one. The diagram above is the fuller target (preview environments, staged traffic, approvals).
- **Container Apps revisions** for blue/green: a new revision receives 10% of traffic until synthetic checks pass, then 100%. Rolling back means shifting traffic to the previous revision. **As built:** the API app is in single-revision mode, and every deploy (a new image, or a provision that changes its containers) starts a new revision, with a new Quickwit sidecar. Container Apps keeps the old revision serving until the new revision's replicas have passed their startup and readiness probes, and keeps it serving if they never do ([Microsoft's revisions docs](https://learn.microsoft.com/en-us/azure/container-apps/revisions#zero-downtime-deployment)). The API's startup probe is `/readyz`, which stays unavailable through loading and the startup warm-up (06 §6.6), so with `minReplicas` above 0 (prod) traffic moves only once the new replica is warm, with both replicas billed meanwhile. That is about 5 minutes after it loads: every prod start from 3 to 10 October 2026 used its whole 300 s warm-up budget (`scripts/logs.sh --env prod --query-name warm-up`) (09 §9.5). The probe allows 780 s there (loading 420 s plus the 360 s readiness cap) and 480 s where the app scales to zero, which keeps a 60 s cap; failing it restarts the container. `az containerapp update` returns once the revision is created, not when it's ready (about 15 s for the deploy of 9 October 2026), and so does a provision's deployment of the app (19 s that evening), so neither times out on a slow start. Only `scripts/ci/roll-api.sh` waits for readiness: it polls `latestReadyRevisionName` for up to 15 minutes; a revision that isn't ready by then fails the deploy and the old one keeps serving.
- **Images:** pinned base `gcr.io/distroless/cc-debian12` (or `scratch` with a musl static build) for the API; the Quickwit image is pinned by digest per environment in `infra/quickwit-image.json`, which `infra/main.bicep` and CI's publish both read. An environment it lists runs our build of v0.9.1 ([ADR-0013](adr/0013-quickwit-from-our-fork.md)), built in that environment's registry by `scripts/build-quickwit.sh` (ACR Tasks, about an hour) or imported from another environment's with the same digest; publish fails if the registry lacks it. Any other environment runs upstream v0.9.1, which publish copies into ACR with that digest unchanged (CI checks it). The ingest image is built on the same pinned image (`Dockerfile.ingest`'s `QUICKWIT_IMAGE`, whose default, upstream's, is what PR builds use). **As built:** image builds pull Docker Hub base images (node, rust, python, quickwit) through Google's Docker Hub mirror, `mirror.gcr.io`, set as BuildKit's `docker.io` mirror in `ci.yml`, because anonymous Docker Hub pulls from shared runners hit its rate limit (two `429 Too Many Requests` publish failures on 9 October 2026). The mirror needs no sign-in, but it caches only frequently pulled images; on a miss BuildKit goes to Docker Hub itself ([Google's docs](https://docs.cloud.google.com/artifact-registry/docs/pull-cached-dockerhub-images)). `scripts/ci/quickwit-image.sh` skips the copy when the registry already has the pinned digest, and otherwise reads from the mirror before Docker Hub. ACR's own artifact cache isn't used: its Docker Hub rules need a Docker Hub account's credentials in Key Vault.
- **Data pipeline deploys** are separate from app deploys. A new `index_version` is published by the `index` job and picked up by the API's refresher, not by redeploying.

## 8.8 Domain and DNS

- Move the `usnewsmap.com` registration to an account the project controls, with auto-renew and at least 2 admins. This was one of the legacy single points of failure.
- Host DNS in **Azure DNS**. All three names point at the one container app, which serves the site and the API ([ADR-0010](adr/0010-site-served-by-the-api.md)):
  - the apex `usnewsmap.com` is an A record to the environment's static IP (an apex can't be a CNAME);
  - `www` and `api` are CNAMEs to the app;
  - each name has an `asuid` TXT record, which Container Apps checks before binding it;
  - `CAA` records allow only DigiCert, the managed certificates' CA.

  **As built:** the zone is `infra/modules/dns.bicep`. Once the delegation is live, `scripts/bootstrap.sh` binds each name to the app with a free managed certificate: the apex by HTTP validation, `www` and `api` by CNAME. It records each certificate so Bicep keeps the binding (§8.9).

- The legacy `/loc_api` endpoints aren't kept: the old site has been offline for years.

## 8.9 Portability: redeploying into another subscription or tenant

The whole system can be stood up from this repository in **any** Azure subscription, in any tenant, with one command, and the corpus rebuilt from public sources. That is a design requirement: no single account, subscription or person is load-bearing (the legacy site's failure mode).

**Command:** `scripts/bootstrap.sh --env <env> [--subscription ID] [--location REGION] [--domain NAME] [--alert-email ADDR] [--ingest]`. It is idempotent: re-running it brings an existing environment up to date. It:

1. checks the sign-ins (`az`, `gh`) and registers the resource providers the templates use;
2. writes the environment's settings (`.azure/<env>/.env`), including:
   - the GitHub repository (and its immutable-ID OIDC form, looked up from the API);
   - whether the subscription's one Cosmos DB free-tier slot is still free;
3. deploys the stack `usnm-<env>` (everything but the API, which has no image yet);
4. creates the **GitHub Environment** of the same name, restricted to the `main` branch, writes that environment's variables, and adds it to the repository variable `USNM_DEPLOY_ENVIRONMENTS`;
5. runs `ci` on `main` (every time, so the registry holds the current `main`), which publishes the images, and waits for that run;
6. switches to the registry (`USNM_USE_ACR=true`) and deploys the stack again, which deploys the API;
7. once the registrar delegates the domain to the zone, binds the apex, `www` and `api` to the app with managed certificates (re-run it after delegating), and removes the Static Web App that used to serve the site;
8. checks the API's `/readyz` and the site.

Then, for a full corpus, start the backfill job and let the weekly ingest job publish (04 §4.4). A **new environment starts with no data**: the system of record is LoC's public data, and everything in Blob and Cosmos is derived from it by a deterministic pipeline. Rebuilding takes ~4.5 h of title sync (LoC's 20-requests/minute API limit) and ~2.5 days of curation (LoC's bulk limit of 10 downloads per 10 minutes per IP; 4 paced workers, the backfill job started again each time an execution ends, about every 23 h), for about $20–30. Hand-curated state belongs in git, never only in an environment: the catalog overrides (place coordinates in `catalog/overrides/places.json`, title records in `catalog/overrides/titles.json`) ship in the ingest image.

**What is per environment, and what is shared:**

| Thing                                                                                                                                                         | Scope                        | Notes                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The deployment stack `usnm-{env}`: resource groups `rg-usnm-{env}` and everything in them (registry, identities, storage, Cosmos, VNet, apps, jobs, DNS zone) | Per environment              | Globally unique names carry a suffix derived from the subscription and environment, so the same environment name works in another subscription                                                                                                                                                                                                          |
| CI identity `id-usnm-ci-{env}`                                                                                                                                | Per environment              | Trusts only jobs in the GitHub Environment `{env}` of the configured repository, which only `main` may use. Rights: AcrPush on its registry, and the "usnm deployer" custom role on its resource group (roll out API images, which also carry the site), and Managed Identity Operator on the API's identity only. No secret is stored or read anywhere |
| GitHub Environment `{env}`                                                                                                                                    | Per environment              | Its variables are written by bootstrap. `publish` (in `ci`) runs once per listed environment                                                                                                                                                                                                                                                            |
| Guard-rail policy definitions (`usnm-deny-*`, `usnm-audit-*`)                                                                                                 | Per subscription             | Their own deployment stack, `usnm-guardrails`, shared by every environment in the subscription; the assignments are per resource group, in each environment's stack, and in `usnm-archive` for `rg-usnm-archive`. Needs Owner (or Resource Policy Contributor) on the subscription                                                                      |
| Cosmos DB free tier                                                                                                                                           | One account per subscription | Bootstrap turns it off for a second environment in the same subscription (~$1–3/month serverless instead)                                                                                                                                                                                                                                               |
| The domain                                                                                                                                                    | One environment              | Only the environment whose zone the registrar delegates to serves `usnewsmap.com`; others use their app's `*.azurecontainerapps.io` name                                                                                                                                                                                                                |

**Prerequisites in the target:** an account with **Owner** on the subscription (role assignments, policy definitions). No tenant-level objects are created (no app registrations; all identities are managed identities), so no Entra admin is needed. On GitHub: admin on the repository (environments and variables). A **fork** works the same way: bootstrap reads the fork's name and ids, and the federated credentials trust that repository only.

**Moving production** to another subscription (or tenant):

1. Run `scripts/bootstrap.sh --env <env> --subscription NEW --domain usnewsmap.com --ingest`. For an environment whose local settings already name another subscription, add `--move`. Without it, bootstrap refuses to rebind an environment to a different subscription. With it, bootstrap resets the settings that describe the old subscription: the registry switch-over, the domain certificates, and the Cosmos DB free-tier check. Use a new environment name if the old one should keep deploying from CI meanwhile: the GitHub Environment `<env>` points at whichever subscription bootstrap wired last.
2. Let the new environment rebuild the corpus, and check it on its app's `*.azurecontainerapps.io` name.
3. Delegate the domain to the new zone's name servers (`scripts/settings.sh --env <env> --key NAME_SERVERS`), then **re-run bootstrap**. Once it sees the delegation, it binds the apex, `www` and `api` to the new app and issues their certificates. HTTPS on the custom names needs this step.
4. The old environment keeps serving until the delegation changes; afterwards, delete it with `scripts/teardown.sh --env <env> --subscription OLD`. That removes only its Azure resources; the GitHub Environment and the settings belong to the new copy.

## 8.10 Naming

Resource names follow [ADR-0017](adr/0017-resource-naming.md) (proposed): `usnm-{function}-{type}-{env}`, for example `usnm-ocr-appi-prod`, with a compact form for storage accounts, registries and Key Vaults (`usnmocrstprodffapzy`) and the deployment suffix after the environment only on names that are unique across Azure.

- **New resources** take the convention from their first commit, in every environment. Dev and experiment environments are fully conventional.
- **Existing prod names** move at natural points: the OCR exchange account and node before the worker is installed, the ingest jobs and scratch account during #283 preparation. The stateful core of prod (`rg-usnm-prod`, `cae-usnm-prod`, `vnet-usnm-prod`, `ca-usnm-prod`, `crusnmprodffapzy`, `log-usnm-prod`, `appi-usnm-prod`, the blob and Cosmos DB private endpoints `pe-usnm-blob` and `pe-usnm-cosmos`), the data lake `stusnmdffapzy` and `cosmos-usnm-prod-ffapzy` keep their names until a rebuild such as the subscription move in §8.9. A rebuild in a new subscription gets a new suffix and comes up under the new names, while the old subscription keeps the old ones until it is torn down. The ADR maps every current name to its target.
- **Names are built in one place**, `infra/naming.bicep`. Scripts and queries read names from stack outputs or tags instead of matching type prefixes such as `caj-usnm-`.
- The names in §8.1 are shorthand from before the build. The live names are in the ADR's mapping table.
