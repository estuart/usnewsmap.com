# ADR-0016: Pluggable OCR engines behind one versioned contract

- **Status:** Proposed
- **Date:** 2026-10
- **Extends:** ADR-0004 (Rust) to the OCR pipeline, and ADR-0015 (on-prem OCR workers)
- **Amends:** ADR-0015 §6, which keeps Python for the engine survey: the survey's runner and scorer move to Rust. Python stays inside engine images whose engine is a Python library, in one-off sampling tools, in audits, and in the Japanese cloud job until that job runs through the contract.
- **Spec:** [13: OCR engines](../13-ocr-engines.md)
- **Related:** [12: On-prem OCR pipeline](../12-onprem-ocr-pipeline.md). 12 specifies the language code map, the damage metric in Rust, the worker's unit and install, the cloud pickup (`usnm-ingest ocr-sync`), the release and the seeder. This ADR and 13 use those pieces under 12's names.

## Context

**How Tesseract came first.** The language report's Fraktur plan ([`report.md`](../../reports/2026-10-language-analysis/report.md), #246) proposed running Tesseract's Fraktur German model (`deu_latf`) and its roman German model (`deu`) on about 1,000 German pages, to confirm the typeface and to serve as a pilot. The first draft of the worker (#298) carried that over, and Tesseract is its only engine. On main:

- `crates/usnm-ocr-worker/src/engine.rs` has an `Engine` trait with one implementation, `Tesseract`. It runs the `tesseract` CLI as one subprocess per page, with `--psm 3 --dpi 300` and the `txt` and `alto` configs.
- The trait takes a path on the host and a language, and returns text, ALTO and an `ocr_engine` string. An engine can only report `Unsupported` or `Failed`, and the worker leaves the message to reappear in both cases.
- `candidates()` hard-codes Tesseract model names per language. `--engine` accepts only `tesseract`, and the worker holds one engine.
- `ocr_source` is the literal `usnm-tesseract`. The stored ALTO is Tesseract's own file with only `fileName` changed.

**The survey grew its own harness.** The engine survey (#296) runs on node 1 and isn't in the repository yet. It runs each engine in its own podman container through a Python runner: Tesseract, docTR, Surya 2 and NDNP Open OCR, with American Stories being added. It has its own job and result formats, page ids and scoring, and its numbers don't describe what the worker would run:

- it runs Debian's Tesseract 5.5.0 without `--dpi 300`, which the worker passes;
- it scores the engines' raw text, not the `normalize_ocr` text the overlay stores;
- its page ids (`<lccn>_<date>_ed1_seq4`) aren't `doc_id`s (`<lccn>_<date>_ed-1_seq-4`);
- it measures resources from inside each container, under limits the worker wouldn't use.

**American Stories was missing.** The first engine list left out the pipeline Dell Research Harvard used to build the American Stories dataset from Chronicling America scans. Its text is already indexed alongside LoC's (#218), and it reads English only. But NDNP Open OCR reuses its layout model, and its legibility classifier may be a damage signal, so it is being added to the survey as a fifth container.

**What the engines look like.** The [engine catalog](../13-ocr-engines.md#1312-engine-catalog), fact-checked on 2026-10-10, covers close to 40 engines, pipelines and model servers. Three things follow from it:

- Only Tesseract, NDNP Open OCR and Kraken write ALTO, in three dialects: v3 in pixels, v3 in inch1200 at an assumed 300 dpi, and v4 in pixels with polygons. The others return word, line or block boxes, or no geometry at all.
- Most are Python libraries. Tesseract and Kraken have CLIs. American Stories' pipeline and NDLOCR-Lite are run today as scripts that load their models on every call. Most vision-language models can run behind llama.cpp's or vLLM's OpenAI-compatible servers.
- Four are Rust libraries: oar-ocr and ocrs, and the PP-OCR ports paddle-ocr-rs and ocr-rs. mistral.rs and Candle are Rust runtimes for vision-language models.
- Many are Apache-2.0, but some models come with terms that reach the published text (Surya 2's modified Open RAIL-M), some are research-only or non-commercial, and some have no licence at all.

**The rule of 2026-10-10.** The OCR pipeline is Rust wherever practical. An engine that is a Python library may keep a thin Python adapter, and a CLI engine gets a small Rust adapter. The contract between the worker and the adapters therefore has to be language-neutral.

**Gaps on main that the design has to close:**

- **Language codes.** The catalog stores MARC codes (`ger`, `cze`; `crates/usnm-core/src/names.rs`), or LoC's lower-cased name for a language not in its table (`pennsylvania german`). The worker expects ISO 639-3. Message validation only checks for three lower-case letters, so a `ger` message passes, routes to a Tesseract model named `ger`, and fails as `no_model` on every node until it is dead-lettered. 12 Steps 4 and 7 add the map and the check.
- **ALTO.** The only ALTO writer is Python (`ja-ocr/alto.py`, v3.1 in inch1200). The worker's only ALTO handling is a string replace of `fileName`.
- **Damage.** The damage metric exists only in Python (`ja-ocr/quality.py`). 12 Steps 4 to 6 port it to `usnm_core::damage`.
- **`loc_text`.** The worker writes the queue reason (`bulk` or `user`) there, and `usnm_ingest::ocr_ja` reads the column as LoC's failure class. Nothing reads `ocr-out` or `curated/ocr-local/` yet; 12 Steps 8 and 9 plan the pickup and the release's reader. Read through `ocr_ja::load`, a worker row with `loc_text = bulk` would count as indexable Japanese text.
- **The worker's unit can't run rootless podman.** `usnm-ocr-worker.service` runs as `usnm` and sets `PrivateDevices`, `ProtectKernelTunables`, `RestrictSUIDSGID`, `RestrictAddressFamilies` and similar options. systemd documents that, for a unit without `CAP_SYS_ADMIN`, these imply `NoNewPrivileges=yes`. Under no_new_privs, `newuidmap` can't use its file capabilities, so podman can't map the subordinate ids `node-setup.sh` gives `usnm`. The unit's comment assumes that leaving out `NoNewPrivileges=` is enough. `ProtectHome=yes` also hides `/run/user`, where rootless podman keeps its runtime state. 12 Step 2 moves the unit to `scripts/ocr-node/usnm-ocr-worker.service`.
- **Node 1** has 8 GB of memory, 2 cores and 4 threads, and no GPU, so engine instances have to share its memory under a budget.

## Decision

1. **One contract, `usnm-ocr-engine/1`.**
   - An engine adapter is the entrypoint of its engine's image. It speaks JSON lines on stdin and stdout. Once it is ready, it sends a `hello`: the engine and its version, every model file any of its profiles can load with its sha256, the profiles it offers with their languages, models and tunable options, and how it cancels a page that runs past its deadline. `engines.lock.json` keeps each image's whole `hello`, and the worker refuses an instance whose `hello` differs from it. After that it takes one `page` request at a time and answers each with one `result`.
   - Images and outputs go through files. The worker writes the scan, or its scaled copy or tiles, into a read-only `/in` mount. The adapter writes the engine's ALTO, or a neutral `boxes.json` with word, line or block boxes in declared units, into `/out/<run_id>/`.
   - The page request carries no page id, URL or batch, only what the engine needs to read the image.
   - The Rust types in a new crate, `usnm-ocr-contract`, are the source of truth. JSON Schemas generated from them serve the Python adapters, and a conformance suite runs against every image. The spec is [13 §13.4](../13-ocr-engines.md#134-the-contract-usnm-ocr-engine1).
2. **Every engine runs in its own image, pinned by digest, as a long-lived instance.**
   - An instance stays up between pages and reads them one at a time until the worker recycles it. Engines that can keep their models in memory do. CLI and script engines (the Tesseract and Kraken CLIs) load their models for each page, and that time is part of the page's measured time; their adapters still save a container start per page.
   - Tesseract runs in a container too. EL9 has no usable Tesseract (ADR-0015), and the survey must run the same artifact as production. Its adapter could later link libtesseract's C API to load models once per profile, if the survey shows the load time matters next to a full page's read.
   - CI builds the images from digest-pinned bases and sha256-pinned models and pushes them to the environment's private registry (`infra/modules/registry.bicep`: Basic, Entra only, CI pushes as `id-usnm-ci-<env>` over OIDC). `ocr/engines/engines.lock.json`, written by CI and reviewed in a PR, pins each image digest and its model hashes. Production never runs an image the lock doesn't pin.
   - The node group gets AcrPull on the registry. The worker pulls by digest with an Entra token from the Arc agent, exchanged for a registry token.
3. **Engines run under a separate account.**
   - A second system user, `usnmeng`, runs rootless podman with its own subordinate ids. It isn't in `himds`, so nothing it runs can read the Arc agent's token challenge.
   - Its user manager runs the Podman API service, with the socket at `/run/usnm-ocr/podman.sock`, shared with the worker through a group. The worker starts and stops engine containers with `podman --remote` over that socket, so it never needs user namespaces itself. Its unit keeps its hardening and adds `NoNewPrivileges=yes`, `RestrictNamespaces=yes` and an empty capability set.
   - Containers run with no network, a read-only root and all capabilities dropped. The container user maps to a subordinate id, not to `usnmeng`. Memory equals memory plus swap, with CPU and pid limits, and scratch space on a size-capped tmpfs, so an engine's files count against its own memory limit and can't fill the node's disk.
   - A spike on node 1 confirms that this works with SELinux enforcing before anything else is built. If it doesn't, this decision is amended.
4. **Rust does everything that decides or records something.**
   - The worker does the routing, the instance pool, deadlines and kills, and resource metering from each container's cgroup.
   - It decodes the scan, scales it and cuts it into tiles where a profile asks (docTR and Surya on full pages). It parses engine ALTO, writes the one stored ALTO, converts boxes to ALTO and merges tiles, extracts text in reading order, strips markup, runs `normalize_ocr`, scores damage with `usnm_core::damage` (12 Step 5) and records provenance.
   - An adapter only runs its engine on one image. It never tiles or merges tiles.
   - Adapters for CLI and HTTP engines, and for engines that can only be run as a script per page, are small Rust binaries: Tesseract, the Kraken CLI, vision-language models behind llama-server or vLLM, and a later oar-ocr. Adapters for engines that are Python libraries are thin Python on one shared helper, and import the engine once: docTR, Surya 2, NDNP Open OCR, American Stories (its pipeline's functions, not its script) and NDLOCR-Lite (its modules, not its `ocr.py`).
5. **One stored ALTO profile.**
   - The worker writes ALTO 3.1 (namespace `ns-v3`, `alto-3-1.xsd`) from parsed values, in pixels of the IIIF full image it fetched. Engine XML is never stored.
   - The page text is derived from that ALTO in reading order, then normalized. Block- and page-level engines put their text in the blocks of `boxes.json`, so the stored text and the ALTO always hold the same words.
6. **Routing is versioned data.**
   - `ocr/engines/engines.toml` lists the engines, their profiles, limits and licence gate.
   - `ocr/routing/routes.toml` holds ordered rules. A rule matches language, script, title, batch, date range, queue reason and damage score, and names an engine and profile, with fallbacks.
   - A profile carries default options (Tesseract: `psm = 3`), and a route's options override them. The dpi comes with the image (300 for a full scan), so every route, the catch-all included, reads at the dpi main passes today.
   - A re-route is a reviewed change to these files with a version bump, and needs no new worker binary. The first release installs the files on the node with the worker. Later, CI publishes them to the registry as one artifact, and the worker polls for it.
   - Messages carry ISO 639-3 and base batch names (no `_verNN`). Validation (12 Step 7) rejects MARC-only codes such as `ger` and `cze`, which then dead-letter at once. `usnm_core::lang` (12 Step 4) maps MARC codes and LoC's pass-through names to ISO 639-3 for the seeder and the survey.
   - A node with no usable engine (image missing, breaker open, cgroup check failed) stops taking messages and backs off, so an engine outage on a one-node fleet doesn't use up the queue's receives.
   - When only some engines are down, the worker peeks, and receives past messages for those engines with a bounded defer: each such message is received at most twice with the usual 1,800 s hide and left, then moved to `ocr-deadletter` with cause `unroutable`, which the seeder queues again after a growing wait and outside the page's limit of 3 attempts. Nodes can't change a message's visibility or put it back on a work queue, so this costs each blocked message up to 3 of its receives, and other engines' pages keep moving. Engines a node can never run get a queue per capability ([13 §13.7.6](../13-ocr-engines.md#1376-choosing-a-candidate)).
   - Each route has at least one candidate. `fallback_after` (receives per candidate before the next) defaults to 2 and is at least 1.
7. **Provenance on every page.**
   - `ocr_source` is `usnm-<engine family>`.
   - `ocr_engine` becomes a tag that code can parse: engine version, profile, image digest, model digest, route, routing version and contract version. Its short key, `<family>/<version> <profile>`, is what the release's engine index and the API use.
   - The ALTO's `OCRProcessing` holds the full digests.
   - A new `runs/` Parquet record, with one row per engine read in a receive that writes a page, holds the full `ocr_engine` tag, digests, options, route, resources, and damage before and after OCR. `ocr-sync` picks it up with the page's part and checks that its `ocr_engine` matches the part's. Reads in receives that write nothing (timeouts, crashes) go to telemetry with the same outcome and resource fields.
   - The overlay schema keeps its 16 columns.
8. **Licences gate production in data.** `engines.toml` holds the list of cleared licences, `production_licenses`, which the maintainer edits. To start: Apache-2.0, MIT, BSD-3-Clause, CC0-1.0, CC-BY-4.0, and, by the maintainer's decision of 2026-10-10 because usnewsmap.com is entirely non-commercial, CC-BY-NC-4.0, CC-BY-SA-4.0 and Datalab's modified Open RAIL-M (`LicenseRef-Datalab-OpenRAIL-M`: Surya 2, Marker and Chandra). Those three are cleared on condition that the site has a credits page naming each engine and model used in production and linking its licence; `routes check` refuses a production route to a model whose licence requires credit unless its entry carries a `credit` line ([13 §13.7.2](../13-ocr-engines.md#1372-enginestoml)). An engine marked `production = false`, or a profile that uses a model whose licence isn't on the cleared list, can be surveyed but not routed in production. The worker and `routes check` both refuse it. Clearing one is the maintainer's decision.
9. **The survey runs the production path.**
   - A Rust binary, `usnm-ocr-survey`, uses the worker's engine host, the same lock and images, and the same profiles, ALTO writer, normalization and damage code.
   - A survey result is keyed by the image digest, model digest, profile and options that a production route would resolve to.
   - Round 1 from the Python harness stays as indicative only. Its Tesseract arm is re-run through the new runner before any routing decision.
10. **One engine per page by default.** A route may add a cascade once a replay of survey results shows the gain is worth the node time. A cascade reads a page with a second engine only when the first leaves its damage above a threshold, and it has guards against a fluent reading that isn't on the page. There is no best-of on every page and no word-level voting across engines.

## Alternatives

We compared three full designs. This decision is the one with a container per engine and JSON lines on stdin and stdout, with parts of the other two added.

| Option                                                                                                                        | Why not                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Engines as socket-activated services: HTTP and JSON on Unix sockets, podman quadlets, a Rust shim in every image              | Its separate engine account, scratch bounded by memory and page requests without page ids are kept above. The rest is heavier and less proven. It has two protocol layers (HTTP outside, JSON lines between the shim and a Python engine) and a shim process in every image, with quadlet and socket units rendered per engine. Images would be built on the operator's machine and copied with scp, with no durable store. Nothing outside the container can kill a stuck engine. It adds a second overlay schema version. Its transport needs the most podman and systemd features that are untested together on EL9 |
| Job directories: `request.json` and the outputs in files, a one-line doorbell, image archives in blob storage, one `ocr.toml` | Its per-model licence gate, the marking of unpinned runs, its extra container limits and its repeat-run check are kept above. It writes the request to a file and rings a doorbell where one line on the pipe does the job. Models load lazily inside the first page's deadline, with no hash check at run time. Resource figures go to telemetry only. Its archives would sit in the exchange account, which has 7-day soft delete and no versioning, and whose firewall keeps CI out. Its worker runs podman from the hardened unit                                                                                  |
| The worker as a user unit of `usnm`, running podman itself                                                                    | The one process that can get tokens would give up its systemd hardening, and would share an account with the engines' container storage                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Tesseract on the host, containers only for the other engines                                                                  | EL9 has no Tesseract to install (ADR-0015). A source build on each node would differ from the surveyed binary, and there would be two production paths                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| A container per page (`--tesseract-bin` naming a podman wrapper)                                                              | Pays a container start on every page, on top of any model load                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Tiling inside each adapter, as the survey does                                                                                | Puts the cut and the removal of duplicate words in Python, once per engine. The worker already decodes and scales the image                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| gRPC between worker and engine                                                                                                | Adds code generation and grpcio to every image, for one page in and one result out, with nothing to stream                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Engines inside the worker's process (`ort`, oar-ocr, ocrs)                                                                    | Code in the worker's process gets no memory cap and no hard kill. `ort`'s only non-yanked releases are 2.0 release candidates. ocrs reads the Latin alphabet only. oar-ocr can still come as its own image behind the contract                                                                                                                                                                                                                                                                                                                                                                                         |
| OCR-D processors                                                                                                              | A METS workspace and PAGE-XML per page, plus a Python layer, where the worker needs one page in and one page out. Its curated model lists are still useful                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Storing each engine's own ALTO                                                                                                | Three dialects in two unit systems. NDNP Open OCR also writes `softwareVersion` 1.2.0 on release v1.2.1. Every consumer would have to handle every engine                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| A new overlay schema version for the provenance fields                                                                        | Touches the shared schema, the Japanese job's Python writer and every reader. A separate runs record carries the new fields                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Best-of on every page, or word-level voting across engines                                                                    | Doubles node time on a 2-core node for a gain the survey hasn't shown. Aligning words across different segmenters is a large job                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## Consequences

- **New code.** Rust crates `usnm-ocr-contract`, `usnm-alto`, `usnm-ocr-route` and `usnm-ocr-adapter` (the CLI and HTTP adapters), and a Python package, `usnm_ocr_adapter`. The damage port (`usnm_core::damage`, cargo feature `damage`), the language map (`usnm_core::lang`), the pickup (`usnm-ingest ocr-sync`) and the release's reader are 12's (Steps 4 to 9). `ocr-sync`'s ALTO checks use `usnm-alto`, and its pickup also takes the runs records. The engine Containerfiles and `models.lock` move into the repository under `ocr/engines/`. The build order is in [13 §13.11](../13-ocr-engines.md#1311-build-order).
- **Node setup changes.** `node-setup.sh` adds `usnmeng` with lingering and its own subordinate ids, cgroup delegation to user managers, the Podman API socket, the tmpfs scratch and a tighter worker unit (`scripts/ocr-node/usnm-ocr-worker.service`, which 12 Step 2 creates). On GPU nodes it turns on the `container_use_devices` SELinux boolean. `offboard.sh` removes them.
- **The registry holds engine images.** The Basic tier includes 10 GiB of storage, and more is billed per GB. Nodes delete images no routing bundle names, and digests that wrote production rows are locked against deletion and overwrite. AcrPull is granted on the whole registry, so nodes could also pull the API and ingest images (code, not data). Repository-scoped permissions would switch the registry to a mode in which AcrPull and AcrPush no longer apply, and every existing grant would have to move.
- **The registry token exchange is new.** It turns an Entra token from the Arc agent into a registry token, and it hasn't been tested with an Arc identity. `podman --remote pull` hands that token to `usnmeng`'s Podman API service, so a compromise of `usnmeng` yields a short-lived AcrPull token for the whole registry.
- **Survey numbers from round 1 are indicative only.** Every survey image's digest changes when its entrypoint becomes an adapter. The round-1 images exist only in node 1's local storage under mutable tags, so they are saved by image id before anything is rebuilt.
- **`curated/ocr-local/` needs its own reader before any release** (12 Step 9). It must not reuse `ocr_ja::load` or `ocr_ja::indexable`, which read `loc_text` as LoC's failure class.
- **A credits page becomes a prerequisite.** No production route to a CC-BY-NC-4.0, CC-BY-SA-4.0 or Datalab-licensed model merges before the site has a credits page naming each engine and model used in production. Kraken's austriannewspapers model, the ocrs weights, Chronicling Germany's models, and Surya 2, Marker and Chandra can then be routed in production. Datalab's terms also put attribution and share-alike conditions on the Output, and the licensor can restrict use remotely; the maintainer accepted these on 2026-10-10.
- **Licence decisions stay with the maintainer.** Until they are made, these engines and models are survey only:
  - research only: CHURRO and Qwen2.5-VL-3B (Qwen Research License);
  - no licence: American Stories' code and weights, Nanonets-OCR2, and UB Mannheim's model files (`frak2021` among them);
  - unknown terms: docTR's default weights from doctr-static.mindee.com (`db_resnet50`), EfficientOCR's `effocr_en` and EasyOCR's weights;
  - HunyuanOCR: it isn't licensed in the EU, the UK or South Korea;
  - Nougat's weights: CC-BY-NC, until the version is confirmed (its nougat-small card says cc-by-4.0);
  - dots.ocr's supplemental agreement, MinerU's attribution clause and NDLOCR-Lite's DINOv3 terms.
- **Block-level engines give coarse geometry.** Their lines and words inherit the block's box, so any later use of their ALTO geometry, such as highlighting, is coarse. The recorded granularity says so, and the survey compares their text by alignment instead of word positions.
- **What an escape reaches.** An engine that escapes its container lands on a subordinate id of `usnmeng`, or on `usnmeng` itself if the escape goes through the runtime (crun or conmon). Neither can reach the Arc token files or the exchange account. `usnmeng` owns the Podman API socket and the engine images, and holds the registry token during a pull. Podman doesn't re-verify image layers when it runs a container. The digest check catches a wrong image, but not tampering inside `usnmeng`'s storage.
- **Engine outages cost receives.** While some engines are down, pages for them use up to 3 of their 5 receives and then wait for the seeder to queue them again. Limits set on cgroups above an engine's own scope are checked too, so a systemd slice can't leave an engine less memory than the scheduler assumes.
- **Contract changes are expensive.** A breaking change means rebuilding every image, so the worker supports versions N and N-1 while it happens.
- **Two ALTO unit systems.** The stored ALTO is in pixels, while LoC's and the Japanese job's are in inch1200. Readers must check `MeasurementUnit`.
